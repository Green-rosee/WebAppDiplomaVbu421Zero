# WebAppDiplomaVbu421Zero

Учебный дипломный проект на ASP.NET Core .NET 10.

Проект представляет собой веб-приложение для выполнения инженерных расчётов,
расчёта трудоёмкости и стоимости,
а также хранения и обработки результатов расчётов. 
Дополнительно проект включает модуль параметрического 3D-моделирования деталей, 
генерацию технических чертежей и интеграцию с GigaChat для автоматического заполнения параметров.

## Основные возможности

- Авторизация пользователей через JWT

- Разделение доступа по ролям
- Работа с несколькими функциональными областями ASP.NET Core Areas

- Расчёт параметров якорных лебёдок
- Параметрическое создание 3D-моделей деталей для судоремонта
- Формирование технических SVG-чертежей
- Использование GigaChat для заполнения параметров детали по текстовому описанию
- Генерация STL и PNG-превью через OpenSCAD
- Расчёт общей трудоёмкости
- Расчёт стоимости одного изделия
- Расчёт итоговой стоимости с учётом количества изделий
- Сохранение выполненных расчётов
- Просмотр истории расчётов
- Интерактивные страницы на Blazor Interactive Server

### SiteAdam

Область для работы с центробежными насосами.

Основные возможности:

- выбор серии насоса;
- ввод параметров насоса;
- выбор нормативного набора;
- подбор ближайших нормативных значений;
- расчёт трудоёмкости и стоимости;
- сохранение результатов и просмотр истории;
- сравнение расчётов по различным нормативным наборам;
- отображение итоговых данных в интерактивной Excel-таблице;
- ручное редактирование таблицы и добавление дополнительных работ;
- сохранение и скачивание Excel-файлов;
- формирование, сохранение и скачивание контракта.

Для отображения Excel-подобной таблицы используется Syncfusion Blazor Spreadsheet.

#### Нормативные наборы

Для расчёта центробежных насосов поддерживается работа с несколькими независимыми нормативными наборами.

В проекте используются демонстрационные Excel-файлы:

- `CollectCentrPumps_A.xlsx`;
- `CollectCentrPumps_B.xlsx`;
- `CollectCentrPumps_C.xlsx`.

Они находятся в каталоге `ExcelFilesPageLoad/CentrPumps`.

Формат данных:

`Series | Impeller | HourImpeller | Weight | HourWeight | Volume | HourVolume`

Для импорта нормативов используется `ExcelDataReader`. Поддерживаются загрузка файла с компьютера пользователя и выбор заранее подготовленного Excel-файла на сервере.

При импорте:

- выполняется проверка на повторную загрузку по `Name` и `FileName`;
- создаётся отдельный `PumpNormativeSet`;
- определяется или создаётся серия насоса;
- импортируются нормативы рабочего колеса, массы и производительности;
- записи связываются с нормативным набором через `PumpNormativeSetId`.

#### Хранение нормативов после импорта

После импорта Excel-файл больше не является непосредственным источником данных для расчёта.

```text
Excel-файл
→ ExcelDataReader
→ сущности EF Core
→ база данных
→ расчёт
```

Нормативные значения сохраняются непосредственно в таблицах базы данных `PumpImpeller`, `PumpWeight` и `PumpVolume`. Исходные Excel-файлы остаются в проекте как исходные справочники и могут использоваться для повторного импорта после пересоздания базы данных.

То есть база данных хранит не только имя или ссылку на Excel-файл — сами нормативные данные после импорта находятся в базе.

#### PumpNormativeSet

Каждый импортированный справочник представлен сущностью `PumpNormativeSet`, которая хранит `Id`, `Name`, `FileName` и `CreatedAt`. Благодаря `PumpNormativeSetId` одна и та же серия насоса может иметь разные нормативные значения в разных справочниках.

#### Жизненный цикл нормативных наборов

На текущем этапе импортированные нормативные наборы автоматически не удаляются из базы данных. Это сделано намеренно, поскольку сохранённые расчёты могут быть связаны с конкретным нормативным набором и должны оставаться воспроизводимыми.

Простое физическое удаление нормативного набора может нарушить связь между историей расчётов и нормативами, по которым были выполнены расчёты.

В промышленной версии целесообразно добавить управление жизненным циклом нормативов:

- признак активности `IsActive`;
- деактивацию устаревших наборов;
- архивирование;
- запрет выбора архивного набора для новых расчётов;
- сохранение возможности просмотра старых расчётов;
- физическое удаление только тех наборов, которые больше не используются историей.

#### Расчёт по выбранному нормативному набору

`CentrifugalPumpService` подбирает ближайшие значения рабочего колеса, массы и производительности только внутри выбранной серии и выбранного нормативного набора.

Трудоёмкость одного насоса:

```text
HourImpeller + HourWeight + HourVolume
```

Общая трудоёмкость:

```text
трудоёмкость одного насоса × количество
```

Общая стоимость:

```text
трудоёмкость одного насоса × количество × стоимость часа
```

#### История и сравнение

В историю сохраняются параметры расчёта, итоговая трудоёмкость и стоимость, а также `PumpNormativeSetId` и `NormativeSetName`. Это позволяет использовать историю как таблицу сравнения одинаковых расчётов, выполненных по разным нормативным наборам.

#### Интерактивная Excel-таблица

Данные истории выводятся в `Syncfusion Blazor Spreadsheet`. Поддерживаются автоматическая загрузка и ручное обновление данных, редактирование ячеек, добавление дополнительных строк, настройка ширины столбцов, сохранение Excel на сервере и скачивание текущего Excel на компьютер.

Перед повторной загрузкой старый диапазон очищается, поэтому удалённые из БД записи не остаются визуально в Spreadsheet.

#### Формирование контракта

Контракт формируется из текущего состояния Spreadsheet, а не напрямую из базы данных. Поэтому в итоговый документ могут попасть данные из истории расчётов, исправленные пользователем значения, дополнительные работы и вручную добавленные строки. Для формирования `.xlsx` используется `ClosedXML`.

### SiteBram

Область для работы с судовыми лебёдками.

На текущем этапе реализован расчёт якорной лебёдки.

Поддерживается:

- загрузка исходных данных из Excel;
- хранение серий лебёдок;
- хранение параметров массы;
- хранение параметров вала;
- хранение параметров цепи;
- формирование допустимых конфигураций;
- подбор ближайшей конфигурации по введённым параметрам;
- указание количества изделий;
- расчёт трудоёмкости;
- расчёт стоимости одного изделия;
- расчёт общей стоимости;
- сохранение расчётов в историю;
- просмотр сохранённых расчётов;
- обновление данных таблицы без полной перезагрузки страницы;
- редактирование Excel-подобной таблицы в браузере;
- экспорт итоговых данных в Excel-документ.

Для отображения и редактирования таблицы используется BlazorDatasheet.

В дальнейшем планируется добавить:

- швартовые лебёдки;
- буксирные лебёдки;
- грузовые лебёдки.

### SiteCerber

Область для параметрического создания деталей, применяемых в судоремонте и производстве.

На текущем этапе реализован модуль создания фланца.

Поддерживается:

- ввод геометрических параметров фланца;
- проверка введённых параметров через FluentValidation;
- автоматическое заполнение формы по текстовому описанию через GigaChat;
- формирование OpenSCAD-модели;
- генерация STL-файла;
- генерация PNG-превью 3D-модели;
- формирование технического SVG-чертежа;
- отображение 3D-превью и чертежа непосредственно в веб-интерфейсе;
- скачивание сгенерированных файлов пользователем.

Для генерации 3D-модели используется OpenSCAD.

В Docker Development дополнительно используется `xvfb`, позволяющий OpenSCAD создавать PNG-превью без графического интерфейса.

Взаимодействие с GigaChat выполняется через HTTP API. 
Секретный ключ передаётся через переменные окружения и файл `.env`, который исключён из Git через `.gitignore`.

Архитектура модуля построена через отдельные сервисы:

- `IOpenScadService` / `OpenScadService`;
- `IGigaChatService` / `GigaChatService`;
- `IFlangeDrawingService` / `FlangeDrawingService`.

Для модели фланца используется отдельный `FlangeModel`, а проверка параметров выполняется через `FlangeModelValidator`.

## Базы данных

Проект поддерживает два режима работы с базами данных.

### Локальный запуск из Rider

При локальной разработке используются SQLite-базы:

- `dbSiteBase.sqlite` — пользователи и авторизация;
- `dbSiteAdam.sqlite` — центробежные насосы и история расчётов;
- `dbSiteBram.sqlite` — якорные лебёдки и история расчётов.

Файлы SQLite не хранятся в GitHub и исключены через `.gitignore`.

### Docker Development

Для разработки через Docker используется PostgreSQL.

Используются отдельные development-базы:

- `webapp_base_dev`
- `webapp_adam_dev`
- `webapp_bram_dev`

Конфигурация находится в:

`docker-compose.dev.yml`

Для начального создания development-баз используется:

`docker/postgres/init-dev.sql`

Development PostgreSQL использует отдельный Docker volume:

`postgres_dev_data`

### Docker Release

Для обычного Docker-развёртывания используется PostgreSQL с отдельными базами:

- `webapp_base`
- `webapp_adam`
- `webapp_bram`

Конфигурация находится в:

`docker-compose.yml`

Начальная структура PostgreSQL создаётся через:

`docker/postgres/init.sql`

Для каждой функциональной базы используется отдельный `DbContext`.

Регистрация контекстов и выбор провайдера базы данных вынесены в:

`ServiceDatabaseRegistration`

В зависимости от конфигурации приложение использует SQLite или PostgreSQL.

## Работа с данными якорных лебёдок

Исходные данные для якорных лебёдок хранятся в Excel-файле и импортируются
в базу данных при её первоначальном создании.

Используются следующие наборы данных:

- `Series`
- `Weight`
- `Shaft`
- `Chain`
- `Design`

Таблица `Design` содержит допустимые комбинации:

`Series + Weight + Shaft + Chain`

Для идентификаторов сущностей используется `Guid`.

Для наследуемых сущностей лебёдок применяется стратегия Entity Framework Core:

`TPC — Table Per Concrete Type`

Подбор конструкции выполняется по ближайшему соответствию введённых параметров:

- масса;
- диаметр вала;
- калибр цепи.

## Авторизация

В проекте используется JWT-аутентификация.

JWT хранится в `HttpOnly` cookie:

`access_token`

Доступ к функциональным областям приложения ограничивается ролями.

Пример:

```csharp
[Authorize(Roles = "Admin,Bram")]
```

Для функциональных областей используются роли `Admin`, `Adam`, `Bram` и `Cerber`.

Начальные пользователи создаются при инициализации базы данных. Для каждого пользователя пароль хешируется через `PasswordHasher<UserAuthz>`. Инициализация выполняется идемпотентно: отсутствующие пользователи добавляются без удаления уже существующих записей.

Пароли пользователей не хранятся в открытом виде.

Для создания и проверки паролей используется:

`PasswordHasher<UserAuthz>`

При инициализации базы пароли преобразуются в хеши,
а при авторизации проверяются через `VerifyHashedPassword`.

## Генерируемые файлы и безопасность

Файлы, создаваемые приложением во время работы, не хранятся в GitHub.

К ним относятся:

- рабочие OpenSCAD-файлы;
- STL-модели;
- PNG-превью;
- SVG-чертежи;
- локальные Excel-файлы;

## Формирование и скачивание Excel-документов

В `SiteAdam` и `SiteBram` поддерживаются два сценария работы с Excel:

- серверное сохранение сформированного файла в рабочую папку приложения;
- скачивание файла пользователем через браузер.

Для скачивания используется Blazor JavaScript Interop. Сервер формирует Excel-файл, преобразует его в поток данных и передаёт браузеру для сохранения на компьютере пользователя.

## Continuous Integration

В проекте настроен CI pipeline через GitHub Actions.

Workflow находится в:

`.github/workflows/ci.yml`

Pipeline автоматически запускается при:

```text
push → master
pull request → master
```

Выполняются этапы:

```text
Checkout repository
→ Setup .NET 10
→ Restore
→ Build
→ Run tests
→ Build Docker image
```

Для интеграционного теста GitHub Actions автоматически поднимает
отдельный PostgreSQL service container.

Таким образом каждый push проверяет:

- восстановление NuGet-пакетов;
- сборку solution;
- unit-тесты;
- PostgreSQL integration test;
- возможность сборки Docker image.

На текущем этапе реализован CI без автоматического CD-развёртывания.
